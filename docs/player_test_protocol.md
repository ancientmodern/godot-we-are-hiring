# 《我们正在招人》首次玩家验收协议

> 状态：**尚未执行 / 未验证**  
> 规范来源：`we-are-hiring-creative-bible.md` 卷六、`requirements_matrix.md` §11、`product_decisions.md`“验收证据状态”  
> 适用对象：首次接触候选构建的真实玩家；开发者、自动模拟和重玩数据均不能替代

## 1. 目的与发布口径

本协议把创意圣经的五个体验问题转成可重复执行、可审计的首玩流程。它测量的是玩家的自发反应，不是功能是否存在。

- 五项发布样本量与通过比例已在 `product_decisions.md`“首次玩家发布门槛”书面批准；下表复述其判定规则。仍须同时报告原始分子、分母、录像时间戳、原话与全部排除原因。
- `ACCEPT-003` 的创意圣经门槛不变：第三章第 4 周文字变化的自然发现率必须在 **15%–30%**（含边界）。
- 每章首玩时长的开发目标为 15/35/50/60/40 分钟，验收窗口为 12–18 / 28–42 / 40–60 / 48–72 / 32–48 分钟。每章至少需要 5 个同一候选构建的有效首玩完章样本，才可报告试点中位数；这仍不替代正式发布样本计划。
- 只有同一候选构建的真人证据达到已批准最小分母与比例，并完成所有失败项重测后，五项体验门槛才可关闭。

## 2. 参与者与场次有效性

### 纳入条件

- 从未玩过本作，也未观看完整流程、策划案、测试报告或他人试玩。
- 能独立阅读当前构建语言，并同意匿名记录屏幕、输入、麦克风和访谈原话。
- 从干净的本地档案开始，不继承开发者存档或 NG+ 状态。

### 排除或单独标记

- 发生阻断流程的崩溃、坏档或主持人代替玩家做出选择。
- 玩家在关键节点前读到剧透，或主持人提示了“债”“第二次使用”“文字变了”“救林越”等目标。
- 开发者、作者和看过创意圣经的人只能计入内部 QA，不进入首次玩家分母。
- 若玩家未到达某测试的资格节点，只从该项分母排除，不应删除其余有效数据。

记录玩家的游戏习惯、AI 产品使用经验、创业/管理经验和近似职能，但不得用这些资料预判或引导其选择。

## 3. 构建与证据准备

每一轮招募前冻结一个候选构建，并建立：

```text
tests/evidence/playtest-YYYYMMDD-build-<id>/
  manifest.md
  sessions/
    P001/
      session.md
      screen.mp4
      input-log.jsonl
      interview.txt
```

`manifest.md` 至少记录：`artifacts/candidate_manifest.json` 的 `production_tree_sha256` 与 `source_tree_sha256`、Godot 版本、操作系统、随机种子/内容版本、招募日期、主持人、已知问题和本轮批准的样本计划。若后来建立 Git 仓库，可同时记录提交号，但不能用提交号替代两项实际文件指纹。参与者使用匿名编号，不把姓名、邮箱写入仓库。

开测前完成以下检查：

1. README 列出的全套自动测试通过，主场景可以从空白档案启动。
2. 录像同时包含完整游戏窗口和声音；麦克风仅在参与者同意后录制。
3. 行为日志至少能定位章节、周、事件 ID、行动 ID、是否委托、读档/重开和结局。
4. 主持人手边有本协议，但参与者看不到验收问题。
5. 为录制、保存期限和删除方式取得知情同意；不同意麦克风时，以观察笔记和访谈原话替代，证据限制必须标注。

## 4. 单场执行流程

### A. 开始前（5–10 分钟）

1. 确认首次接触与录制同意，分配匿名参与者编号。
2. 只说：**“请按你自己的方式经营这家公司；可以随时说出你正在想什么。这里没有需要猜的测试答案。”**
3. 不解释融资判定、隐藏债、作者权重、林越路线或文字变化。
4. 让玩家自己输入公司名并开始；只有操作设备或严重无障碍问题可获得中性帮助。

### B. 游玩中

- 主持人保持安静，不提示最优行动，不问“你注意到了吗”。
- 在关键节点只记时间戳和可见行为，不打断玩家。
- 玩家主动提问设计含义时回答：**“先按你的理解继续，结束后我们会聊。”**
- 玩家想读档或重开时不得阻止，也不得提醒存档存在；记录其主动意图与实际行为。
- 完整记录暂停、卡住、误触、主持人介入和技术故障。

### C. 结束后访谈（10–15 分钟）

按顺序提问，先开放、后具体，避免把目标词塞给玩家：

1. “你会怎么向朋友描述这个游戏？”
2. “它让你想到什么？”
3. “有没有哪一刻让你意外、停下来，或者改变了你后面的玩法？”
4. “你注意到过界面或选项文字有什么变化吗？”若玩家自行提到，再追问何时、哪里、如何确认。
5. “你为什么第一次把工作交给它？后来为什么又用/没用？”
6. 若林越已离开：“她离开后你最先想做什么？”不要主动问“会不会重开救她”。

逐字转录关键回答；总结不能替代原话。

## 7. 汇总与版本判断

每个候选构建单独汇总，不把不同文案/数值版本混入同一分母。报告至少包含：

- 招募数、各项资格分母、排除数与排除原因；
- 五项的原始计数、分母和匿名证据链接；
- `ACCEPT-003` 的发现率、样本量和区间估计；
- 五章有效首玩时长的中位数与范围；
- 所有主持人介入、录制缺口和已知偏差；
- 对照已批准发布门槛逐项给出通过/失败计算；
- 失败后修改的构建号，以及旧证据到新证据的版本链。

禁止以下替代证据：单元测试通过、开发者自评、代理/机器人模拟、文案在源码中存在、截图看起来正确、重玩者知道答案后的反应。
